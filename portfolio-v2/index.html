01 / Context & current challenges

New product integration required extensive copying

02 / Legacy system

Clone frontend, backend, and DB objects per product

With Angular and .NET Framework 4, the team selected the closest existing product, cloned its database objects and frontend/backend code, then implemented the differences.

Columns represent product-specific code and database objects; they do not imply separate databases or servers.

Duplication across layers

Fragmented maintenance

The same behavior lived in multiple copies, increasing the number of places to check when shared business rules changed.

Unclear reuse boundaries

Product-specific behavior was mixed with reusable behavior, so each new branch carried another copy of the existing code.

Legacy integration flow

03 / Improvement approach

Reuse Setting Types instead of cloning products

Phase 1 — through early 2024: replaced per-product cloning with Product ID → Setting Type ID configuration. The integration staffing and lead-time improvements below belong to this phase.

Phase 2 — from 2024: modernized to React/.NET 8 in line with the company’s Docker/Kubernetes direction, moved to on-premises Linux, and retired 2 Windows Server machines.

Separate units of behavior

Each Setting Type has an identifier and an implementation shared across products; unsupported behavior is added only when needed.

Map through configuration

A Product ID maps to a set of Setting Type IDs. When all types exist, a product is added through mapping configuration instead of copying application layers.

Modernize the web application

Migrated Angular and .NET Framework 4 to React and .NET 8 Minimal APIs, combining shared design with collaboration across Database, QC, and PM/BA.

05 / New system

A shared application configured per product

After modernization, Customer Setting ran on on-premises Linux in line with the company’s Docker/Kubernetes direction; 2 legacy Windows Server machines were retired. The diagram below shows logical application components, not Kubernetes topology.

New integration flow

With the legacy approach, even cloning a similar product required retesting all copied code. Mail Station.

Centralized management.
Distributed execution by team.

Role: Technical Lead — Web & Database · 2015 — 2017 · Team of 5

01 / Context & current challenges

Distributed jobs without a central view

Each team managed internal jobs with its own tools. When jobs for a partner needed to be reviewed or stopped, the company lacked a central inventory to identify every active task.

When a partner contract ended, the lack of a central job inventory made it difficult to identify and stop every related task, creating a risk of continued data delivery after the contract had expired.

02 / Legacy system

Team-owned scheduling and operations

Team jobs

Teams primarily used Windows Task Scheduler for internal tasks, with schedules and operations spread across teams.

Database team jobs

The Database team used SQL Server Agent and Database Mail to email results after job completion.

No shared inventory

There was no shared administration page to search by partner, monitor status, and control all internal jobs.

03 / Improvement approach

Central administration, execution at the Client

One configuration source

Admin stores job information, cron, email configuration, and team permissions in SQL Server; Clients fetch current configuration at startup.

Messaging-based control

Request/Response retrieves job information. Pub/Sub carries cron changes and Run/Stop/Cancel commands; business logic remains in the Client JobTask.

Availability monitoring

Clients send a heartbeat every minute. Job List shows Not Available when the latest heartbeat is more than 5 minutes old.

Initiated the platform and built core functionality

Technical Lead — Web & Database in a team of 5. Initiated the project, researched and selected technologies, and designed and implemented RabbitMQ/EasyNetQ messaging for configuration retrieval, cron updates, job control, and heartbeats. Built core functionality, specified pages and features, supported team members, and reported progress to the Manager.

05 / New system

Shared Admin, team-owned execution

This overview shows the main components and logical connections. The sequence diagrams below describe each workflow in detail.

On startup, Clients clear old cron-change, Run, and Stop/Cancel messages, then retrieve current job information, cron, and HoldOn status through Request/Response. Held jobs remain waiting; otherwise cron is registered. Admin must be ready first to respond.

Admin publishes changes without waiting for Clients to be online. Running Clients update their schedules on receipt. A Client starting later fetches the latest cron from Admin; an additional message with the same cron does not trigger another schedule change.

A Client subscriber receives Run commands and calls JobTask.Run(). Jobs are also triggered by the local cron scheduler; execution results are reported to Admin and stored in the database. The email library calls an SMTP server to send notifications.

Run() checks cancellationToken at each step and passes it to async methods that support cancellation. Commands use Pub/Sub; receiving a command does not mean the job has stopped immediately.

Admin updates the up time field to now in SQL DB for the Job ID when a heartbeat arrives. This field records the latest heartbeat time. Not Available means no heartbeat has been received for more than 5 minutes; it does not confirm that the process has terminated.

When the database is under high load and the Database team is investigating, Admin persists HoldOn job status in SQL DB and publishes TemporaryHoldOn. Clients receive the notification, request cancellation of running jobs through cancellationToken, stop cron, and enter a waiting state.

HoldOn status is included in the job information returned at Client startup. A Client restarting during the hold therefore retrieves the current state from Admin rather than depending solely on an earlier Pub/Sub notification.

Only Admin updates HoldOn status. While held, Run now and Stop controls are disabled; Clients do not register cron to start new jobs.

After the DBA confirms database readiness, Admin first updates job status in the database to Normal, then publishes ContinueWorking. Clients reuse the startup flow: clear old messages, fetch current job information and status through Request/Response, and register cron again from configuration.

This is an operator-controlled hold/resume mechanism. Job cancellation is cooperative; restoring cron does not imply resuming a job from its interrupted step or automatically replaying missed schedules.

Architecture case study / 04

Data Warehouse.

Consolidated accounting data.
Queue-based Excel exports.

Role: Technical Lead — Web & Database · 2012 — 2014 · Team of 4

.NET Framework 4 (x64)SQL ServerSQLite QueueAsync Excel Export · EPPlus
01 / Context & current challenges

Large exports disrupted the website

The system consolidated accounting data and exported Excel reports. Large exports frequently caused OutOfMemoryException, forcing DBAs to query and deliver customer data manually.

Concurrent exports made the website unresponsive, overloaded the server, and affected other websites on the same host. Queries spanning more than three months could take over 10 minutes; the original developers had left, making legacy analysis harder.

02 / Legacy system

Queries and Excel generation inside the web process

The website ran queries and generated Excel in the web-serving process. A DataSet loaded the entire result into memory before writing files; the Windows 32-bit environment made memory limits a critical bottleneck.

03 / Improvement approach

Separate exports from the website and bound memory use

Queue and Export Service

The website writes requests to a SQLite queue. Two Export Services on two servers process requests, isolating heavy work from the web process.

Query the relevant data

The Database team split data by age across three databases on three servers and tuned stored procedures. Export Service queries the relevant databases concurrently for the report period.

Stream rows and split files

DataReader reads one record at a time; each Excel file contains at most 5,000 rows. Files are zipped and delivered through an emailed download link.

04 / Individual contribution

Built the application and services

Technical Lead — Web & Database in a team of 4. Analyzed the legacy system, proposed the solution, and implemented the website, Export Service, SQLite queue, monitoring job, and reference report page.

The Database team owned database splitting and stored procedures, including performance tuning. After core services were completed, newer team members implemented additional report pages using the reference page.

05 / New system

The website accepts requests; services process and deliver results

Both services share a SQLite queue. Connections to the three databases indicate query targets selected according to the requested date range.

New export flow

  1. Accept a requestUsers sign in, choose a reporting period, and submit an export request. The legacy ASP.NET website was upgraded to .NET Framework 4 (x64), preserving business behavior, refreshing the UI/UX, and inserting a record into the SQLite queue table.
  2. Claim work and queryTwo services periodically poll the queue. Each processes one request at a time, allowing two different requests to run concurrently. For each request, the service identifies the relevant databases, calls their stored procedures concurrently, and combines the results.
  3. Batch Excel outputDataReader reads rows sequentially and writes them directly to the current Excel file. At 5,000 rows, the service saves and closes the file, then creates another if data remains. The final file is saved even with fewer than 5,000 rows. Only one workbook of up to 5,000 rows stays in memory at a time, avoiding OutOfMemoryException from accumulating all results in one workbook. Processes run on .NET Framework 4 (x64).
  4. Deliver resultsWhen the Excel files are ready, Export Service compresses them into a ZIP file and emails a download link. Users can continue using the website during processing. The on-screen preview uses 100-row pagination.

Operations & limitations

Partition databases by time range

Data previously resided in one central SQL database. The upgrade moved it into three physically separate SQL databases by data age: the 7-day database holds days 1–7, DB14 holds days 8–14, and DBArchive holds day 15 onward. Based on the user's selected date range, Export Service calls stored procedures concurrently on the relevant databases and combines their results.

Isolate heavy workloads

Exports run in separate processes on two servers. If one service stops, the other can continue claiming pending requests. The website continues accepting requests through the queue table.

Scale with demand

The number of instances consuming the queue can increase or decrease. Automatic scaling depends on deployment mechanisms and load signals. The two services require atomic request claiming to ensure each request is assigned to only one service at a time.

Monitor requests stuck in Running

If an Export Service stops unexpectedly while processing, its claimed request remains in the Running state in the queue table. The other service continues claiming pending requests.

A separate monitoring job checks the queue table. If a request remains in the Running state for more than 24 hours, the job alerts the development team's room for investigation and manual resolution.
